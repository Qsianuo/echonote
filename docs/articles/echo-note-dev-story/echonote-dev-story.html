01

PART

 

我们要做的是什么

PROJECT BACKGROUND & GOALS

事情要从一个不太复杂的场景说起：开完一场会，脑子里还热乎着，想把刚才讲的话录下来、转成文字、存成字幕，方便后面整理。但你不想联网——会议内容、未发表的想法、个人随笔，这些都不该被悄悄传到某台看不见的服务器上。

市面上现有的工具大致两类：云端 API（快但要联网），或者本地 Whisper（准但要么卡要么重）。真正开箱即用、边说边出字幕、还完全离线的，反而少见。EchoNote 就是想补这个缺口。

核心目标只有三条：

  • 本地：音频不出本机。默认走本地 ASR，远程识别是可选的。
  • 实时：说一句话，2.8–3.4 秒内首条字幕出现在屏幕上，1.0 秒内定稿。
  • 准：默认模型（medium）在中文短句上 CER 0.0%（理想情况），不是「能看懂就行」的程度。

技术栈也很朴素：Python 后端 + 浏览器前端 + WebAudio 录音 + faster-whisper / sherpa-onnx 双 ASR 后端。没有 GPU 依赖，一台普通笔记本就能跑。

目标听起来不大，但每一个都是「看起来一行代码，实际上一堆坑」。

我们做了一个决定：不做创新，做严谨。模型用现成的，算法用成熟的，我们的精力全部投入到「把每个细节理解清楚并用测试钉死」。听起来很枯燥，但这恰恰是工具类项目能活下来的原因。

PART

 

这一轮我们真正做完的事

WHAT WE ACTUALLY SHIPPED

这轮迭代（v0.12.0）大致可以分成四块。我按「做了什么、为什么做」的顺序说。每一块都有它自己的「为什么」，跳过任何一个都讲不清楚后面。

1. 边录边落盘——录音不再只在内存里

v0.11.x 时代，录音是全在内存里的 ArrayBuffer。录 30 分钟还好，录两小时就容易崩。浏览器的内存上限、垃圾回收抖动、意外刷新，任何一样都能让一段辛苦录好的音频彻底消失。

v0.12.0 把它换成了 OPFS（Origin Private File System）边录边落盘：

  • 每 0.6 秒切一段 PCM，异步写进浏览器私有文件系统；
  • 落盘和识别解耦——落盘慢不影响字幕，字幕卡不影响落盘；
  • 出 WAV / SRT / Markdown 时流式导出，不再一次性加载整个文件。

这里踩到一个坑：FileSystemFileHandle.move() 只有 Chrome 有。Firefox 和 Safari 要走 createWritable() + file.stream().pipeTo() 做流式拷贝改名。如果只在 Chrome 上测试，上线一周后就会收到一堆 Firefox 用户的报错。

2. 回放 + 字幕 seek——录完还能回头看

落盘之后，回放就是自然而然的下一步：

  • 点时间戳跳到对应音频位置；
  • 字幕和波形同步高亮；
  • 30 秒窗口解码，一次只读 0.96MB 的 Int16 PCM，不一次性 load 整段。

性能优化上做了两件事：PcmLedger 字节记账（overBudget / byteLength 用 O(1) 累加，替代原来 Wav.byteLength(chunks) 的 O(n) 遍历）；波形几何缓存（measure() 是唯一读 getBoundingClientRect 的地方，其余走缓存，渲染 30fps 上限）。回放时波形不再一顿一顿。

3. sherpa-onnx 流式后端——比快更快

原本只有一个 ASR 后端：faster-whisper。它的 large-v3-turbo 确实准，但 rtf（实时率）2.48，也就是一段 10 秒的音频要等 24.8 秒才能出结果——这根本不叫「实时」。

sherpa 走的是 int8 量化，161MB，不需要完整语言模型，速度快一个数量级。可拼写的热词走 modified_beam_search，否则走 greedy。代价是模型不如 Whisper 通用，但对中文短句的场景足够。

同时加了远程识别（OpenAI 兼容 API），但默认关闭，并且带严格模式——音频要出本机，必须用户明确同意，不能默默打开。

4. 三轮尾音修复——一句话的最后三个字

这是这轮迭代里花时间最多、也最值得说的部分。先看现象：

用户录完一句「今天天气很好适合出门」，字幕最后却成了「今天天气很好适合出」。尾部 1–3 个字符消失了。

一开始所有人都以为是 ASR 的问题。我们去查 _clean（ASR 文本后处理）的四个子函数：

  • _collapse_repetition——用正则把 5 次及以上重复折叠成 1 次。丢 4/8/12 个字符，不可能只丢 1–3 个。
  • _strip_echo——ECHO_MIN_CHARS = 6，只删 6 个字符以上的回声串。不可能丢 1–3 个。
  • _is_hallucination——len(core) > 12 直接返回 False，只处理 ≤12 字的整行丢弃。不裁尾。
  • UtteranceStream.apply 的 _SHRINK_GUARD = 0.55——这才是真凶。

_SHRINK_GUARD 的逻辑是：当新假设的文本长度小于旧文本的 55% 时，判定为「灾难性缩水」，拒绝更新。但它只拦「丢一半」——15 个字变 13 个（丢 2 个）、15 个变 14 个（丢 1 个），都在 55% 以上，于是被静默接受。尾巴就这么丢了。

修复方案是加一条更细的判据：

. . . python

if grew > 0 and self._text.startswith(cleaned) and len(cleaned) < len(self._text):

　　self._rejected += 1

　　return False

当新文本恰好是旧文本的前缀、且比旧文本更短时，旧文本严格更好——保留它，保留尾巴。

补了两个测试：一个是 cut=1/2/3 的尾部截断必须被拒，另一个是「今天天气很好适合出错」这种真正的尾部修正必须被接受。

但 bug 不只在这。

回头追更底层的地方，发现 VAD_TAIL_KEEP_MS 才是第一道防线——这一参数决定 VAD 在判定静音后多长的尾音保留给解码器。



CASE

三轮尾音修复

VAD_TAIL_KEEP_MS · covers_end · _SHRINK_GUARD

第一轮：150ms 尾音太短，ASR 拿不到完整音节，解码只能给到「出」。第二轮：改 400ms，但平均 RMS 判静音失效，把有声的尾音当成纯静音丢掉。第三轮：改 1000ms，用 np.any(np.abs(tail_audio) > silence_floor) 而不是平均 RMS，并把 covers_end(end_s) 比到 duration_s（缓冲末尾），不只是 end_s。

结果：end 时间戳和 audio 长度是两个独立语义，不能为「让两者一致」改 end，那会污染字幕时间轴。正确做法是让解码缓冲比 end 略长，去吃掉那点尾音。

那些「想多了」和「想少了」

OVERSHOT & UNDERSHOT

写代码的过程里，有几件事挺有意思。

Windows SAPI 引擎 8.9 秒音频等 23.9 秒无输出。我们想给 Windows 用户一个零依赖的语音识别兜底方案。结果 SAPI 的 SpeechRecognizer 不支持文件流输入，只能走麦克风实时流。用 ffmpeg 把音频「喂」给它也不行。最后只好放弃 Windows 原生这条路，转而推 sherpa-onnx（跨平台、不依赖语言模型）。

GitHub releases 301 被阻断只能走 hf-mirror。用户在海外，下载 sherpa 模型走 GitHub Releases，301 重定向到对象存储被墙了。改走 hf-mirror（HuggingFace 镜像）才通。这提醒我们：只要涉及「用户要下载模型」，就必须考虑多源分发。

models/hotwords.txt 才是生效路径。热词配置一开始放在 config.py，后来发现 sherpa 后端读的是 models/hotwords.txt——两边改一处，另一边默默没生效。后来专门做了一致性检查。

CER 计算陷阱。我们一度测出「medium CER 78%」，吓一跳。查了半天发现参考文本里带了文件头，计算 CER 时把文件头也算进去了。去掉文件头后是 0.0%。测试脚本的参考文本一定要干净。

实现者的「顾虑」字段是计划缺陷的主要发现源。这轮我们用 SDD（规格驱动开发）流程写实现计划。每个实现者在 plan 里写「顾虑」——我担心 XX 可能有问题。后来发现，所有真正被踩到的坑，都在「顾虑」里提前写过。这个字段比任何 review 都管用。

幻觉刷屏。有一段时间，前端会莫名其妙刷出一堆「嗯」、「啊」、「好的好的」，密集到几乎覆盖整屏。排查下来，tiny 模型在安静片段下会编词，_is_hallucination 的 len(core)>12 又拦不住短行。我们后来加了 models/hotwords.txt 词表（用户自定义的高优先词），并在 sherpa 后端用 modified_beam_search 让热词真正生效。tiny 填词表后 CER 从 27.6% 降到 13.8%——不是银弹，但能用。

Windows SAPI 的「想多了」。我们一开始假设「Windows 系统自带语音识别总能用吧」，结果花了两天发现它是为「实时麦克风」设计的，文件流输入根本不支持。假设越接近「常识」，越要早点验证。

数据：延迟到底是不是达标

LATENCY NUMBERS

我们坚持延迟要以语音起点为原点。如果以「说完」为原点算延迟，必然是负数（因为你已经说完了），截断到 0 毫秒。这种口径毫无意义。

这里有个反直觉的点：精度和延迟往往成反比。要快（sherpa rtf 0.126）就要牺牲通用性；要准（whisper large-v3-turbo rtf 2.48）就要牺牲延迟。没有「全都要」的银弹，只有按场景取舍。

我们的做法是默认 sherpa、可切 whisper：日常中文短句，sherpa 又快又准，够用；要处理长段专业内容或者英语，切到 whisper large-v3-turbo，多等十几秒。给用户选择权，而不是替用户做决定。

延迟口径这件事，我们内部也吵过。一开始有人建议「用说完后到结果出来的延迟」，因为这个数字「看起来更短」。但用户感知的延迟是「我说完话，多久看到字幕」——原点必须是语音起点。好看的数据不等于对的数据，这是产品和工程之间永恒的拉扯。

我们学到的几件事

WHAT WE LEARNED

第一，不要相信「常识」。Windows SAPI 自带语音识别、OPFS 一定有 move()、GitHub releases 一定能下载、参考文本一定是干净的——这四个「常识」每一个都让我们踩过坑。越觉得「这肯定没问题」的地方，越要早点去验证。

第二，bug 的根因经常不在你第一眼怀疑的地方。尾字丢失，第一反应是 ASR 后处理（_clean），但真正的三个原因分别在 VAD 尾音保留（150ms）、流式文本收缩守卫（55% 阈值）、和「语义边界」（covers_end 比错对象）。真正定位一个 bug，往往要把整条链路走一遍。

第三，测试不是形式，是「钉子」。每一个修过的 bug，都对应一个测试。cut=0..5 的 6 个尾部截断用例，本质上是把「我修好了」这句话变成机器可验证的事实。没有测试的修复，只是「我猜我修好了」。

第四，给用户选择权。sherpa 快、whisper 准、远程强——但没有一个是「最好」。我们的做法是：默认值选一个最稳的（sherpa），其他作为可选项暴露出来。工具的价值不在于替用户决定，而在于把决定权交回去。

一句话总结

WHAT WE LEARNED

EchoNote 是一个「为了省 100 毫秒而认真」的项目。我们没有做模型创新、没有做算法突破，我们做的事情是：把每一个「看起来是一行代码」的地方，真正理解清楚它的语义、边界、和浏览器差异，然后用测试把它们钉死。

尾部丢 3 个字，根因在 VAD 的 150 毫秒尾音保留、在 _SHRINK_GUARD 的 55% 阈值、在 covers_end 比到 end_s 而不是 duration_s——三个各自正确、合起来就错的地方。这不是玄学，这是工程。

每一个「看起来一行代码」的地方，都值得被认真理解。

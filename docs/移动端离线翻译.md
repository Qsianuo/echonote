# 移动端离线翻译（Android / ONNX 路线）

> 桌面端走 ctranslate2（`app/translate.py`），安卓端没有 Python，改走 ONNX
> Runtime + 纯 Kotlin 分词器。同一个模型（Opus-MT 77M，双向），译文应当
> "读起来一样"；两端实现是两套代码，靠模型文件与词表严格对齐。

## 一、链路总览

```
web/app.js ──config{translate_to}──▶ native-boot.js ──▶ native-translate.js（桥）
                                                            │ Capacitor
                                                            ▼
                                              SherpaMTPlugin.kt（ORT 推理）
                                                        │
                                    MtEngine：encoder → decoder → decoder_with_past
                                                        │
                              SentencePieceModel.kt（unigram Viterbi 分词/解码）
```

- 模型目录：`files/models/mt-zh-en`（中→英）、`files/models/mt-en-zh`（英→中）
- 每个方向 5 个文件：`encoder-int8.onnx`、`decoder-int8.onnx`、
  `decoder-past-int8.onnx`、`mt-src-vocab.txt`、`mt-tgt-vocab.txt`
- 单方向约 **226 MB**（int8），不进 APK，装好模型 `available()` 才会把该语向
  报给前端，界面上的「译文语言」下拉才会出现。

## 二、从零生成模型（桌面侧）

```bash
# 1. 导出 ONNX（encoder / decoder / decoder_with_past / merged）
optimum-cli export onnx --model Helsinki-NLP/opus-mt-zh-en \
    --task text2text-generation-with-past model-dist/mt-onnx/mt-zh-en

# 2. 词表映射：Marian 的合并词表（65001）≠ .spm 的 id（0..31999），
#    导出「片段→合并id→分数」与「id→片段」两张表，Kotlin 只读文本
python tools/export_mt_vocab.py model-dist/mt-onnx/mt-zh-en models/mt-zh-en

# 3. int8 动态量化（fp32 单方向 580 MB，量化后 226 MB）
python tools/quantize_mt_onnx.py model-dist/mt-onnx/mt-zh-en

# 4. 本机冒烟：不装 transformers 也能翻，核对译文与量化前的差异
python tools/mt_onnx_smoke.py model-dist/mt-onnx/mt-zh-en
```

英译中把上面命令里的 `zh-en` 换成 `en-zh` 再来一遍。

> **导出目录不要放在 `build/` 下。** `packaging/build.ps1` 开工第一步就递归删除
> `build/`，1.5 GB × 2 的 fp32 ONNX 会跟着一起消失（2026-10-27 实测踩过一次，
> 最后从模拟器 `files/models` 里把 int8 三件套取回来才没重跑）。统一用
> `model-dist/mt-onnx/<方向>/`，该路径已进 `.gitignore`。

### 踩过的坑（都有测试锁着，见 `tests/test_mt_onnx.py`）

| 坑 | 症状 | 对策 |
|---|---|---|
| 量化用了 `per_channel=True` | 模型能跑、不报错，英文输出退化成 "the the the" | `per_channel=False`（per-tensor） |
| 只量化 MatMul，漏了 Gather | 体积只降一半（词嵌入 33M 参数走 Gather） | `op_types_to_quantize=["MatMul","Gather"]` |
| `decoder_model_merged.onnx` | If 控制流量化器进不去，352 MB → 352 MB | 退回「首步 + 增量」两份普通图 |
| decoder 起始符写成 `</s>` | **每句都翻出空串**，无任何报错 | HF 的 Marian 用 `pad`(65000) 起头 |
| source 不补 `</s>` | 解码进重复循环 `real-real-real-real` | 编码后追加 eos（桌面端同款坑） |
| 每步都从上一步取 `present.*.encoder.*` | 第二步就 KeyError | cross-attention 的 K/V **只在首步算一次**，全程复用 |

## 三、原生库：两份 ORT 如何共存

sherpa-onnx（ASR）自带一份 `libonnxruntime.so`（1.28.2 定制构建），翻译用的
onnxruntime-android 也带一份。同一进程里**只能有一份同名 so**，而两边的
GNU 符号版本互不兼容（实测互相报 `cannot locate symbol "OrtGetApiBase"`，
连改版本串/版本索引都骗不过 bionic）。

解法：给官方那份换 soname（`libonnxruntime.so` → `libonnxrt_1280.so`，
等长替换），让 JNI 的 DT_NEEDED 一起改指过去。于是：

- `libonnxruntime.so` = sherpa 的 1.28.2，只服务 ASR
- `libonnxrt_1280.so` = 官方 1.28.0，只服务翻译
- 各自与自己的 JNI 精确配对，谁也不用将就谁；代价是 APK 增加约 16 MB/ABI

```bash
# 下载 AAR（阿里云镜像）→ 改 soname → 落位 jniLibs 与 app/libs
python tools/pin_ort_jni.py --version 1.28.0 --name libonnxrt_1280.so
```

`.so` 与 `.jar` 都在 `.gitignore` 里（120 MB+ 的预编译产物不入库），
新环境跑一遍上面的命令即可复原。

```bash
adb push <dir>/<file> /data/local/tmp/ && adb shell chmod 644 /data/local/tmp/<file>
```

## 五、译文术语质量（实测，不是估计）

77M 的 opus-mt 会把 `ring light` 翻成「戒指灯」。一开始怀疑是量化或词表，
用 `tools/mt_term_eval.py` 的 12 条带术语的句子分别跑两套**完全独立**的推理栈：

| 后端 | 解码方式 | 术语命中 |
|---|---|---|
| 安卓 ONNX int8 | 贪心（与 `MtEngine` 同算法） | 8/12 |
| 桌面 ctranslate2 int8 | beam 4 + `no_repeat_ngram_size=3` | 8/12 |

**错的是同样 4 条，错法一模一样。** 换成 beam search 一条都救不回来，说明
既不是量化误差、也不是解码策略，而是 77M Marian 的短语表本身没收录这些搭配：

| 英文 | 出来的中文 | 为什么 |
|---|---|---|
| `ring light` | 戒指灯 | ring→戒指、light→灯，逐词素直译 |
| `telecentric lens` | 远程中心镜头 | tele+centric 两个词素都拆错 |
| `exposure time` | 接触时间 | exposure 在非摄影语境被当成「接触」 |
| `depth of field` | 镜头的深度 | field 被整个丢掉，句子还通顺，最容易漏 |

对策不是换模型（77M 的价值就是单句 50~100 ms），而是 `web/mt-repair.js`
做**定向修复**：只在译成中文、且英文原文真的含该术语、且译文里出现实测得到的
错串时才替换，别的字一个不动。两端译文都经过 `app.js` 的 `onFinal` /
`onRefine`，所以修一次桌面和手机都吃。规则全部来自实测输出，加规则前先用上面
的脚本复现一条错译；`tests/js/mt-repair.test.mjs` 锁着。

要彻底解决只有换更大的模型（NLLB-200-distilled-600M 一类），代价是
体积 ~1.2 GB/方向、单句延迟上到秒级——实时字幕体验会明显变差，暂不做。

## 六、模型分发

226 MB/方向的模型不进 APK，也不进 git。发布时作为 **Release 附件** 挂在
每个版本上：

<https://github.com/Qsianuo/echonote/releases/latest>

- `mt-zh-en-int8.zip` ≈ 148 MB（中→英）
- `mt-en-zh-int8.zip` ≈ 147 MB（英→中）

zip 里是「方向目录 + 5 个文件」，`sha256` 与 zip 同目录发布。模型来源
Helsinki-NLP/opus-mt（CC-BY-4.0），量化脚本在 `tools/quantize_mt_onnx.py`，
任何人都能复现同一份产物。

### 装模型：应用内下载（v1.0.4 起）

设置页「离线翻译模型」两块，各自一个「下载」按钮：原生侧从上面这个 Release
拉 zip（154 MB → 解压 237 MB），先对 `*.zip.sha256` 校验，再解压到外部目录。
装完「译文语言」下拉立刻出现，不用重启。

- 需要同时腾出 **约 390 MB**（zip + 解压结果），空间不够会直接拒绝并报可用量；
- 下载中可取消，取消会删掉半截包；
- 拿不到 `.sha256`（老版本没挂该资产）时不拦下载，但结果会标 `verified:false`；
- 安装位置 = `/sdcard/Android/data/com.echonote.app/files/models/`（见下），
  用户想手动清理直接删目录即可，应用内会重新显示「未安装」。
- **发版提醒**：地址用的是 `releases/latest/download/<同名资产>`，所以每个
  新版本都必须继续挂这两个 zip，否则老用户的应用内下载会 404。

代码位置：原生 `SherpaMTPlugin.modelStatus/downloadModel/cancelDownload` +
`MtArchive`（解压/校验，JVM 单测见 `MtArchiveTest`）；界面 `web/mt-models.js`，
桥接 `web/native-translate.js`。

### 手动安装（备选，仍然有效）

插件按「先内部、后外部」找模型，两处都放时以内部为准：

| 位置 | 谁能写 | 用途 |
|---|---|---|
| `/data/data/com.echonote.app/files/models/` | 仅 adb 调试包（`run-as`） | 开发、自动化测试 |
| `/sdcard/Android/data/com.echonote.app/files/models/` | 应用内下载 / 文件管理器 / `adb push` | 签名包的常规位置 |

release APK 不可 `run-as`，所以正式安装的用户用第二个位置——不需要任何
存储权限，解压后目录长这样：

```
/sdcard/Android/data/com.echonote.app/files/models/
├── mt-zh-en/{encoder-int8.onnx, decoder-int8.onnx, decoder-past-int8.onnx, mt-src-vocab.txt, mt-tgt-vocab.txt}
└── mt-en-zh/{同上}
```

推模型（大文件必须走 `/data/local/tmp` 或直接 push 到 sdcard，`adb exec-in`
超过 ~70 MB 会静默截断）：

```bash
adb push mt-zh-en /sdcard/Android/data/com.echonote.app/files/models/
```

放好后重开应用，「译文语言」下拉里就会出现对应语向；没装的方向不会出现在
选项里，也不会出现「点了没反应」。

## 七、启动速度不是文件系统的问题

早先记的「同一份文件，F 盘目录 7 秒、中文名目录 58 秒」，用同一段代码在两个
卷上各跑 4 轮证伪了：

| 位置 | 首次（冷缓存） | 稳定后中位数 |
|---|---|---|
| `F:\echonote\EchoNote-desktop`（exFAT） | 1.64 s | **1.59 s** |
| `D:\echonote-desk-d`（NTFS） | 6.23 s | **1.60 s** |

两盘稳定后差 0.01 s，6 秒只出现在**刚拷过去**的目录上（系统还没缓存这些文件）。
所以 exFAT 不是原因，早先几十秒的差异来自冷热缓存与首次扫描，不是卷格式。
